## 6.2.1 클라이언트 사이드 로그

> 사용자가 **어떤 아이템을 클릭하고, 어떤 행동을 했는지 등 사용자의 서비스 이용 과정과 결과를 기록한 로그**
> 

추천 시스템에서는 단순히 추천 결과만 보는 것이 아니라, **추천된 아이템을 사용자가 실제로 어떻게 이용했는지** 확인하는 것이 중요함

### 1. 사용자 행동 로그

> 사용자가 서비스 안에서 수행한 행동을 기록한 로그
> 

대표적인 예시 → **행동 로그**

- 어떤 화면에서 어떤 아이템이 표시되었는지
- 아이템이 몇 초 동안 사용자에게 노출되었는지
- 사용자가 어디까지 스크롤했는지
- 아이템을 클릭했는지
- 구매, 저장 등 특정 행동으로 이어졌는지

예를 들어 추천 시스템에서 `상품 추천 → 상품 노출 → 클릭 → 구매` 와 같은 사용자 행동 흐름을 기록할 수 있음

이러한 로그는 **추천 모델 학습 데이터**로도 사용할 수 있고, 서비스 제공자가 의도한 대로 사용자가 서비스를 이용하고 있는지 확인하는 데도 사용

### 2. 성능 로그

> 사용자가 요청한 페이지가 실제로 표시될 때까지 걸리는 시간이나 사용자의 조작이 처리될 때까지 걸리는 시간을 기록함
> 

추천 모델의 정확도가 아무리 높아도 **추천 결과가 너무 늦게 나타나면 사용자 경험이 나빠질 수 있음**

따라서 다음과 같은 정보를 기록함

- 페이지 로딩 시간
- 추천 결과가 나타날 때까지 걸린 시간
- 사용자 입력에 대한 반응 시간

즉, **추천 정확도뿐만 아니라 추천 결과를 얼마나 빠르게 제공하는지도 중요함.**

### 3. 에러 및 크래시 로그

> 웹 브라우저나 애플리케이션에서 발생한 오류나 비정상 종료를 기록함
> 

특정 환경에서 오류가 반복적으로 발생하는지 확인할 수 있음

- 특정 브라우저에서 오류 발생
- 특정 스마트폰 OS에서 오류 발생
- 특정 OS 버전에서 앱 크래시 증가
- 푸시 알림 전송 실패

이러한 로그를 이용하면 `특정 환경에서 오류 증가 → 원인 파악 → 수정` 과 같은 방식으로 서비스 안정성을 개선할 수 있음

## 6.2.2 서버 사이드 로그

> 클라이언트 뒤쪽에 있는 **서버 시스템의 동작 상태를 기록한 로그**
> 

서버 로그는 **서비스 내부 시스템이 어떻게 동작했는지**를 중심으로 기록함

### 1. 성능 로그

> 클라이언트의 요청을 서버가 처리하고 응답하는 데 걸리는 시간을 기록함
> 

예를 들어 사용자가 추천 페이지를 요청했을 때 `사용자 요청 → 서버 추천 처리 → 결과 반환`까지 얼마나 걸렸는지를 확인

이를 통해

- 추천 API 응답 시간
- 서버 처리 시간
- 추천 결과 생성 시간

등을 측정할 수 있음

### 2. 시스템 응답 로그

> 클라이언트의 요청 수, 응답 수, 정상 응답 비율 등을 기록함
> 

예를 들어 추천 아이템을 요청했는데 **반환할 아이템이 없는 경우**도 로그로 남길 수 있음

다음과 같은 지표를 확인

- 전체 요청 수
- 정상 응답 수
- 오류 응답 수
- 정상 응답 비율
- 추천 결과가 없는 비율

특히 추천 시스템에서는 **추천 가능한 아이템이 존재하는지**를 통해 추천 범위를 나타내는 커버리지(Coverage)를 확인하는 데 활용할 수 있음

### 3. 시스템 처리 정보 로그

> 서버 내부에서 발생하는 각종 처리 상태를 기록함
> 

대표적으로

- 캐시 히트 비율
- CPU 사용량
- 메모리 사용량
- 서버 오류
- 예외 발생 정보

등을 기록함

예를 들어 추천 응답 속도가 갑자기 느려졌다면 `응답 속도 저하 -> 서버 로그 확인 -> 캐시 히트율 감소? / CPU 처리 능력 부족? / 메모리 부족? -> 원인 분석` 과 같이 활용 가능

## 클라이언트 로그 vs 서버 로그

| 구분 | 클라이언트 사이드 로그 | 서버 사이드 로그 |
| --- | --- | --- |
| 중심 | 사용자 및 사용자 기기 | 서버 시스템 |
| 주요 목적 | 사용자가 어떻게 행동했는지 확인 | 시스템이 정상적으로 처리했는지 확인 |
| 대표 정보 | 노출, 클릭, 스크롤, 구매 | 요청, 응답, CPU, 메모리 |
| 성능 정보 | 페이지가 사용자에게 표시되는 시간 | 서버가 요청을 처리하는 시간 |
| 오류 | 브라우저·앱 오류, 크래시 | 서버 오류, 예외 |
| 추천 시스템 활용 | 사용자 행동 데이터 및 모델 학습 | 추천 서비스 성능·안정성 분석 |

‼️ 추천 시스템에서는 두 로그를 **같이 보는 것이 중요**

**클라이언트 사이드**

`추천 노출 → 사용자 클릭 → 구매`

**서버 사이드**

`추천 요청 → 모델 처리 → 서버 응답`

**추천 모델의 성능 + 사용자 반응 + 시스템 성능을 함께 분석할 수 있음**

## 중요하게 본 내용

- 가장 기억에 남는 내용: 추천 시스템에서는 추천 모델의 정확도뿐만 아니라 사용자 반응과 시스템 성능도 함께 고려해야 한다는 점
- 중요하다고 생각한 이유: 추천 모델의 정확도가 높더라도 응답 속도가 느리거나 오류가 자주 발생하면 사용자 만족도가 낮아질 수 있기 때문
- 다른 주제와 연결되는 부분
    - 암묵적 피드백: 클릭, 조회, 구매 등의 사용자 행동 로그를 활용하여 사용자의 선호도를 추정할 수 있음
    - 추천 시스템 평가: 클릭률(CTR), 전환율(CVR) 등 실제 사용자 행동을 기반으로 추천 성능을 평가할 수 있음
    - 추천 시스템 운영: 서버 응답 시간, 캐시 히트율, CPU 사용량 등을 분석하여 추천 서비스의 안정성과 처리 성능을 개선할 수 있음

## 질문 및 토론거리

- 이해가 어려웠던 부분
    - 클라이언트와 서버에서 모두 성능 로그를 수집하는데, 두 로그의 측정 기준과 활용 방식이 구체적으로 어떻게 다른지 궁금했음
    - 추천 결과가 존재하지 않는 경우의 로그를 활용하여 추천 시스템의 커버리지를 어떻게 측정할 수 있는지 궁금했음
- 팀원들과 함께 이야기할 질문
    - 추천 정확도가 높은 모델과 응답 속도가 빠른 모델 중 실제 서비스에서는 어떤 모델을 우선적으로 선택해야 할까?
        - **노시은**: 속도가 크게 느려지지 않는 한 정확도를 우선시 해야 사용자들이 이용하는데 의미를 느낄 것 같다.
        - **이윤성**: 장기적인 관점 및 시스템 안정성 측면에서 고려했을 때 정확도가 높은 모델이 더 우선시되어야 한다고 생각한다.
        - **이동민**: 기본적으로 제공되는 서비스에는 응답 속도가 빠른 모델을 사용하고 사용자의 요청을 받거나 하는 능동적인 행위가 이루어지는 방식에 정확도가 높은 모델을 사용하는 것도 가능할 것 같다.
        - **안현지**:  서비스의 성격에따라 우선시 되어야되는 것이 다를 것이기 때문에 하고자하는 목표에 맞는 것을 선택해야될 것 같다. 가장 좋은 것은 두가지를 모두 균형있게 선택하는 것 같다.
    - 추천 결과에 대한 사용자 반응이 좋지 않을 때, 추천 모델 자체의 문제인지 서비스 UI/UX의 문제인지 어떻게 구분할 수 있을까?
        - **노시은**: 모델을 바꾸어서 사용자들에게 소개했을 때도 여전히 반응이 좋지 않다면 서비스 UI/UX의 문제라 판단할 수 있을 것 같다.
        - **이윤성**: 평점이나 코멘트 등을 LLM을 활용하여 분석하거나, 종류별 특징량 값의 추이를 비교하여 분석하는 방향으로 피드백을 진행한다.
        - **이동민**: 사용자 로그에 따로 적절한 속성을 넣어서 판단하는 것에 도움을 줄 수 있을 것 같다.
        - **안현지**: 클라이언트 로그를 보고 판단할 수 있을것 같다.

## 스터디 후 보완

- 새롭게 이해한 내용: 서비스의 특성에 따라 빠른 응답이 필요한 상황에서는 경량 모델을 사용하고, 사용자가 직접 정교한 추천을 요청하는 상황에서는 정확도가 높은 모델을 사용하는 등 상황에 따라 모델을 다르게 활용할 수 있음
- 수정하거나 추가할 내용
    - 클라이언트 로그와 서버 로그를 함께 분석하면 추천 결과에 대한 사용자 반응뿐만 아니라 응답 속도 저하나 오류 발생 등 시스템 측면의 문제도 파악할 수 있음
    - 추천 결과가 없는 요청의 비율과 추천 시스템의 커버리지는 서로 다른 개념이므로 구분할 필요가 있음
        - 추천 결과가 없는 비율 → 전체 추천 요청 중 빈 추천 목록이 반환된 비율
        - 아이템 커버리지 → 전체 추천 대상 아이템 중 실제 추천에 등장한 아이템의 비율
