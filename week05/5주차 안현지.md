## 배운 내용 정리

**6.1.3 ~ 6.1.4 요약**

아이템이 너무 많을 때 추천을 빠르게 하는 2개 방법

1. **다단계 추천**: 한 번에 다 계산하지 않고 여러 단계로 나눠 점점 좁혀 간다
2. **근사 최근접 탐색**: 모든 아이템과 비교하지 않고 가까운 영역만 비교해 빠르게 찾는다.

### 1. 다단계 추천

- 처리를 **후보 선택 → 스코어링 → 재순위**로 나눠서 먼저 대략적으로 거르고 후보가 줄어든 뒤에 정확한 모델로 엄선하는 방법
    - '후보 선택'과 '스코어링/재순위' 둘로 나눠 **2단계 추천(two-stage recommendation)**이라고도 한다.
- 필요한 이유: 상품과 사용자가 많은 서비스에서 정확한 모델로 모든 아이템을 계산하면 시스템 부하가 너무 크다.
- 예시 흐름
    
    
    | 단계 | 아이템 수 | 하는 일 | 채용에 비유 |
    | --- | --- | --- | --- |
    | 후보 선택 | 10,000개 이상 → 100~10,000개 | 가벼운 방법으로 빠르게 후보를 추림 | 서류 전형 |
    | 스코어링 | → 10~100개 | 무거운 머신러닝 모델로 점수를 매김 | 면접 |
    | 재순위 | → 사용자에게 제시 | 다양성과 비즈니스 로직을 고려해 순서 조정 | 팀 배치 |
- **후보 선택**
    - 막대한 아이템에서 추천 후보를 뽑는다. 
    예: 유튜브는 수십억 개를 100~10,000개로 줄임
    - 사용자 요청마다 빠르게 응답하기 위한 전처리라서 처리가 가벼워야 한다.
    - 여러 후보 선택 로직을 조합해 다양한 관점에서 후보를 뽑을 수 있다.
- **스코어링**
    - 대상이 줄었으므로 부하가 높은 머신러닝 모델로 정확하게 점수를 매긴다.
    - 예: 인스타그램은 후보 500개에 대략적인 모델부터 정교한 모델까지 차례로 적용해 100개 → 50개 → 25개로 거른다.
- **재순위**
    - 비슷한 아이템만 연달아 나오지않게 순위 전체의 균형과 밀집도를 고려해서 나열
    - 다양성, 콘텐츠 고유 정보를 활용해 사용자 경험과 비즈니스 로직을 반영하는 단계

### 2. 근사 최근접 탐색

- **최근접 탐색 문제**
    - 5장의 알고리즘은 공통적으로 사용자와 아이템을 벡터로 표현하고 벡터의 유사도로 추천함
    - 사용자 벡터와 가장 가까운 아이템 k개를 찾는 문제⇒최근접 탐색 문제
    - 문제점: 모든 아이템과 유사도를 계산하면 아이템 수만큼 응답이 느려져 사용자 만족도 하락함
- **근사 최근접 탐색**
    - 정확성을 일부 희생하고 가까운 벡터를 빠르게 찾는 방법
    - 개인화 추천뿐 아니라 연관 아이템 추천(아이템 → 비슷한 아이템)에도 가능
    - 2단계로 진행
        1. 아이템(사용자) 벡터에 인덱스를 붙인다.
        2. 그 인덱스를 사용해 추천한다.
- **인덱스 원리**
    - 벡터 공간을 여러 영역으로 나누고 각 아이템이 어느 영역에 속하는지 미리 기록
    - 추천할 때는 사용자 벡터가 속한 영역을 찾고 그 영역 안의 아이템만 유사도를 계산
    - 장점: 계산 대상이 줄어 빠름
    - 단점: 영역 밖에 더 유사한 아이템이 있을 수 있어 정확성이 일부 손실
        
        ⇒ 쉽게 말하면 전국 식당과 거리를 다 재는 대신 지도를 동네별로 나눠 두고 우리 동네 식당만 비교하는 것
        
    
    #### 인덱스 시점과 방법 선택
    
    - **벡터 생성·업데이트 시점에 따른 3가지 방법**
        
        
        | 경우 | 처리 방식 | 장점 | 단점 |
        | --- | --- | --- | --- |
        | ① 아이템·사용자 벡터 모두 일 단위 생성 | 매일 벡터 생성 → 인덱스 → 추천 | 항상 최신 | 계산 비용이 큼 |
        | ② 사용자 벡터만 일 단위 생성 | 주 단위: 아이템 벡터·인덱스 / 일 단위: 사용자 벡터·추천 | 일 단위 부하가 낮음 | 새 아이템은 다음 주까지 추천 불가 |
        | ③ 모델을 유지하고 일 단위로 벡터 생성 | 처음에 모델 저장·전체 인덱스 / 일 단위: 신규 아이템만 인덱스 추가 | 전체 인덱스는 한 번만 | 기존 아이템은 같은 인덱스를 계속 써서 정확도 하락 우려 |
- ①에서 인덱스를 매일 다시 붙이는 이유: 행렬 분해나 item2vec을 재학습하면 같은 데이터라도 최적화의 무작위성 때문에 어제와 오늘 벡터의 차원 의미가 달라짐
- 협조 필터링 기반 추천에는 ①, ②를 많이 사용하고 ③은 유사 이미지 검색이나 콘텐츠 기반 추천에서 많이 사용
- 실무에서는 인덱스를 언제 붙일지 먼저 검토한 뒤 전체 설계를 진행할 것을 권장
- 근사 최근접 탐색 도구 선택
    - 대표 도구: LSH, NMSLIB, Faiss, Annoy
        
        데이터 크기와 서버 성능에 따라 선택
        
        | 데이터 수(N) | 기본 선택 | 상황별 대안 |
        | --- | --- | --- |
        | 100만 미만 | Faiss 선형 탐색 (근사 아닌 엄밀한 탐색, GPU 유무에 따라 gpu/cpu) | 느리면 nmslib(hnsw) |
        | 100만~10억 | nmslib(hnsw) | 데이터 추가가 느리면 falconn, 부분 집합 탐색은 rii, 여러 프로세스 호출은 annoy |
        | 10억 이상 | Faiss: hnsw + ivfadc | 메모리 부족 시 PQ의 M을 작게, 정밀도를 높이려면 IVF의 nprobe를 크게 (대신 느려짐) |

## 중요하게 본 내용

- 가장 기억에 남는 내용: 추천 시스템은 정확한 모델 하나로 끝나는 게 아니라 가벼운 방법과 무거운 방법을 단계별로 나눠 쓴다는 점과 정확도와 속도를 둘 다 잡기 위한 설계라는 게 인상적이었다.
- 중요하다고 생각한 이유:  5장에서는 알고리즘의 정확도만 비교했는데 실제 서비스에서는 아무리 정확해도 응답이 느리면 사용자가 떠난다. 근사 최근접 탐색처럼 정확성을 조금 포기하더라도 속도를 확보하는 판단이 중요하다고 느꼈다.
- 다른 주제와 연결되는 부분: 5장의 행렬 분해, item2vec 등이 만든 벡터를 실제로 빠르게 검색하는 방법이 근사 최근접 탐색이다

## 질문 및 토론거리

- 이해가 어려웠던 부분: 근사 최근접 탐색 도구 선택 표에 나오는 HNSW, IVF, PQ 같은 용어가 낯설어서 이해하기 어려웠다. 각 방법이 벡터를 어떻게 나누거나 압축해서 빠르게 찾는지 더 알아보고 싶다.
- 팀원들과 함께 이야기할 질문:
    1. 근사 최근접 탐색에서 정확성을 얼마나 포기해도 괜찮을까? 서비스 종류에 따라 기준이 달라질까?
        1. **김민서**: 추천 정확도가 사용자의 경험을 해치지 않을 정도로 정확성을 포기하는게 좋을 것 같다.
        2. **노시은**: 정확도가 크게 떨어지지 않는 선에서는 빠르게 추천하는 게 좋을 것 같다. 
        3. **이윤성**: 대략적인 추천 범위인 경우에는 정확성이 일정 정도 감소하더라도 빠른 추천이 도움이 될 수 있을 것 같다.
        4. **이동민**: 기존 최근접 탐색에서 근사 최근접 방식에 비교해서 정확성이 덜 떨어지는 걸 확인하는 것도 좋은 방법일 것 같다.
    2. 인덱스 시점 ②처럼 새 아이템이 일주일간 추천되지 않는 문제는 어떻게 보완할 수 있을까?
        1. **김민서**: 새 아이템은 신규 추천을 도입해서 추천할 수 있도록 한다.
        2. **노시은**: 신규순으로 추천하는 방법을 추가하여 보완한다. 
        3. **이윤성**: 주 단위 아래 간접 연관이 되는 일 단위 추천 정보를 증가시켜 간접 보완을 도모한다.
        4. **이동민**: 주기를 줄이고 저장되거나 연산하는 정보량도 단축시키는 방식을 추가할 수도 있다.

## 스터디 후 보완

- 새롭게 이해한 내용: 근사 최근접 탐색 도구들은 결국 ”어떻게 빨리 찾을까"를 다르게 푸는 방법이다.
    - HNSW: 벡터를 길(그래프)로 연결해 따라가며 찾는다.
    - IVF: 벡터 공간을 영역(동네)으로 나눠 그 안에서만 찾는다.
    - PQ: 벡터를 대표값 번호로 바꿔 압축해서 메모리를 아낀다.
    - M과 nprobe는 조절 손잡이: M을 작게 하면 메모리는 줄지만 정확도가 떨어진다. nprobe를 크게 하면 더 많은 영역을 뒤져서 정확해지지만 느려진다. 결국  속도·메모리와 정확도는 트레이드오프 관계다.
- 수정하거나 추가할 내용: 새 아이템이 일주일간 추천되지 않는 문제(인덱스 시점 ②)는 다음 방법으로 보완할 수 있다.
    - 신규순 추천으로 따로 노출하기
    - 콘텐츠 정보로 비슷한 영화 옆에 붙여 주기
    - 새 아이템만 매일 인덱스에 추가하기
